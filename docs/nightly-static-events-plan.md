# 西安静态活动库：夜间增量采集修订方案

> 后续规则以 [静态活动数据采集实施设计](static-events-collection-design.md) 为准：用户已确定 MediaCrawler 七平台，采集阶段经纬度允许为空、最终发布必须补全，固定 12 类以及三个时间字段 DEFAULT NULL。本文保留上一轮实现状态和调研记录，其中“三平台”“经纬度始终 NOT NULL”和待补队列等旧建议不再作为目标设计。

更新：2026-11-12。以用户最新约束为准，取代原 Qovia 采集方案与拆分活动/时段表建议。

## 2. events 表：原 18 列，只解除三个 NOT NULL

| 字段 | 新约束 | 语义 |
| --- | --- | --- |
| start_at | TEXT，可 NULL | 可参加开始时间未知时留空，不等于全天开放 |
| end_at | TEXT，可 NULL | 可参加结束时间未知时留空，不推测散场 |
| suggested_duration_minutes | INTEGER，可 NULL | 未知建议时长留空，不强制估计 |
| latitude / longitude | 继续 REAL NOT NULL | 地点与 WGS-84 坐标未确认，不写入最终活动库 |

其他字段、表名和行结构保留；本轮不新增 source_url 列，不改 guide_url 列，不建 event_sessions 或 activities。信息源与核验过程放在 provenance sidecar；collection 最终数据契约升为 xian-events/2，事件对象对应原 18 列，source_url 移入对应 provenance 记录。

旧库通过事务重建解除三列限制：保留已有行、主键、自定义列、显式索引/触发器、外部引用与调用方原外键设置，失败回滚。不会用 seed 清库。不支持在外层事务内部执行此 schema 迁移，调用方必须提供事务边界。

不带日期的附近发现可包含未知时间记录；带 date 的查询仍只匹配已知完整窗口。规划器对缺任一时间边界返回 unknown_event_window，不抛 NULL 异常，也不允许模型补造时间。已知完整窗口、仅建议时长为空时，可在明确窗口内作规划估计，但不能声称是官方建议。

## 3. GitHub 采集工具调研

核验了各项目 GitHub README 和仓库维护状态。以下为技术候选，均未在本机登录、安装或实测，不承诺当前账号环境一定可用。

| 项目 | 实际适用点 | 限制与结论 |
| --- | --- | --- |
| [NanmiCoder/MediaCrawler](https://github.com/NanmiCoder/MediaCrawler) | 一套 Python/Playwright 框架支持小红书、抖音、B站关键词搜索、指定详情、创作者；支持 JSON/JSONL 等输出及登录态缓存 | 最符合三平台统一接入需求；README 明确仅学习参考、禁止商业用途，不能把它当无条件可商用的依赖。首次需正常登录，登录态过期会影响静默运行 |
| [JoeanAmier/XHS-Downloader](https://github.com/JoeanAmier/XHS-Downloader) | 小红书已有链接的内容采集、搜索结果链接提取 | 适合补详情；搜索结果链接提取不等于已验证的无人值守关键词搜索。README 提到浏览器 Cookie 自动读取功能失效。GPL-3.0，先作为独立工具评估 |
| [JoeanAmier/TikTokDownloader](https://github.com/JoeanAmier/TikTokDownloader) | 抖音数据采集，README 标记支持抖音搜索数据 | 抖音专项备选，Cookie 状态和当前搜索链路需实测；GPL-3.0，不默认复制进本项目 |
| [Johnserf-Seed/f2](https://github.com/Johnserf-Seed/f2) | 多平台采集/下载框架 | README 的部分抖音搜索能力标为开发状态，不能仅凭表中方法名就认定已稳定。暂不优先作为搜索主源 |
| [Nemo2011/bilibili-api](https://github.com/Nemo2011/bilibili-api) | 曾提供较全面 B站 API 封装 | 仓库已于 2026-07-06 归档，当前 README 内容也已变化，不作为新夜间任务的首选长期依赖 |

当前建议：先评估 MediaCrawler 三平台搜索/详情导出，再按实际缺口选择独立专项工具。可先通过其 JSONL 输出接本项目清洗流程，不把第三方依赖、浏览器配置和平台 Cookie 混入主 Agent。

配置初值：只采集帖子/视频标题、描述、原始 URL、发布时间和必要图片链接，不采评论/个人关系，不下载完整视频。每平台单并发、小配额、请求间隔及退避遵守平台访问条件。遇到登录过期或验证需求，记录 login_required 并停止该来源，不在夜间弹窗反复尝试，不绕过访问控制。

“开源”主要节省按次查询费用，不意味着没有浏览器资源、账号维护或适配成本。小红书/抖音的活动海报若关键信息只在图片中，仍需后续 OCR/视觉提取；B站简介没有时间地点时不能用视频标题硬填。

## 4. 搜索来源重新分工

- DeepSeek：公开网页搜索、主办方公告和必要详情补查；deepseek-flash 做正文结构化提取。
- 三平台本地采集：作为发现与补充来源，按关键词和已知主办方账号采集。先一平台一关键词几条内容验证，再扩展。
- Qovia：运行时网络调用已强制返回 QOVIA_DISABLED，配置不再要求或读取 QOVIA_KEY。本地 .env 中用户原有值没有被删除或输出；旧试验结果保留供历史对照，不会被当作新的采集结果。

## 5. 经纬度的独立补全

1. 提取明确的场馆/分馆名称及地址，排除“地址报名后通知”和多场馆歧义。
2. 先匹配项目已核实地点与本地场馆缓存，不能把同名分馆混用。
3. 未命中则独立检索“西安 + 场馆全名 + 详细地址 + 地图位置”，获取可追溯的 POI/坐标来源；需要地理编码时单独选择服务并按其配额执行。
4. 检查行政归属及来源坐标系，转换并保存 WGS-84。不能让模型凭记忆产生坐标，也不能将城市中心点当作活动地址。
5. 缓存场馆匹配结果、原始来源及坐标转换依据；同一场馆的活动复用，不每条都重复联网。
6. 仍无法确认时留在待补文件，不写 events。允许时间空不代表允许经纬度空。

当前仅有验证与字段门槛，尚未接通新的地理编码服务。此前小样本没有坐标的候选仍不因此变成合格数据。

## 6. 夜间静默执行与时效

建议未来本机任务使用 Asia/Shanghai 每晚一次，默认部署候选时间为 02:00；这只是配置建议，当前没有创建 Windows 任务或 Codex automation。

```text
获取互斥锁、检查登录态与本地配置
 → 从上次成功水位回看一段重叠窗口，抓近期新增/更新资料
 → 去重，内容哈希未变且已有有效解析则复用
 → DeepSeek 定向补查、模型提取、坐标补全
 → 事实和字段校验
 → 评估活动时效，生成可发布批次及拒绝/待补列表
 → SQLite 短事务增量 upsert，保留已有 ID
 → 输出 sidecar、批次 manifest、计数及错误日志
 → 释放锁、静默退出
```

- 初始公开资料回看 30 天；后续每晚以成功水位回看至少 48 小时，降低搜索索引延迟和边界漏抓。各平台单独记录水位，某平台失败不能推进它的水位。
- 文档发布时间、抓取时间、事实核验时间和活动日期分别记录。刚抓取的旧文章不能自动刷新活动有效期；同文重复抓取不改变 firstSeenAt。
- 优先复核未来 14 天活动，尤其临近开场、临时调整与取消公告。静态夜更无法保证当日临时取消实时同步，来源和核验时间必须可见。
- `collection/freshness.ts` 已实现基础决策：已取消或已结束排除；按上海日期判断确认的结束日；核验超过 36 小时视为待复核；结束时间未知且无确认结束日期的记录首次发现后最多保留 7 天，来源发布时间超过 30 天又没有结束依据则暂停推荐。
- 时间未知但近期资料已核实且坐标完整：只用于发现，不允许自动排具体日程。上述阈值为初值，可按小样本结果调整，不代表来源正确性的 SLA。
- 不把抓取失败、页面删除或登录失效直接解释为活动取消。只取消当前渠道任务，记录异常，不用失败批次覆盖已有成功库。
- 同时启动两次任务只允许一个执行。关闭交互式终端、日志不打印 Cookie/Key，不采集过程中要求输入，也不自动购买代理或第三方服务。

## 7. 原表不加状态列时，时效如何生效

不能只记录 sidecar 然后假定数据库查询会自动理解它。当前 freshness 函数是可测试规则，仍需采集发布入口及读库边界显式使用。

建议保留稳定的主库记录以供历史行程 ID 回查；nightly sidecar 按 ID 保存来源、状态、首次发现、最近获取、最近核验、确认结束日期及可推荐标志。发现/规划查询应应用有效 ID 集合；getByIds 仍可回查历史并附状态说明。已知 date 查询的 SQL 本身会排除缺时间记录，但这不能替代未知日期记录的 TTL 过滤。

数据与 sidecar 发布必须共享批次 ID/哈希，由发布入口验证一致后切换；失败保持旧批次，不直接替换正在被服务打开的数据库文件。最终采用短事务原地 upsert 或版本目录切换，要在夜间发布入口实现时测试锁与读者行为。

这一层尚未接入现有 EventRepository，因此本轮不能承诺“每天自动清理过期资料已经上线”。也不会清空 events 或每天运行 mock seed，更不能删除历史行程仍引用的 ID。

## 8. 下一步顺序

1. 在这个分支验证三平台工具输出与正常登录态，首先各几条，报告真实成功率、耗时及字段质量。
2. 接入场馆缓存和坐标检索，先补齐已有小样本的地点。
3. 接夜间增量入口：水位、状态 sidecar、互斥锁、失败恢复、upsert 与读取过滤。
4. 先手动运行一个夜间批次并验收，再安装本地静默定时任务；这一步之前不扩大数据量。

每阶段代码完成默认测试通过后推进；平台需要首次正常登录时应明确交接，不能用绕过登录来实现所谓完全静默。
