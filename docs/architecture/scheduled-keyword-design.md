# 定时补充搜索词库与脚本设计

日期：2026-11-13。本轮仅设计“搜什么、用哪个引擎、什么时候搜、搜多少”，不展开数据库维护，不创建系统定时任务。

## 1. 当前能运行的配置

`configs/collection.example.json`是当前统一入口实际支持的配置，内容保持不变：

```json
{
  "city": "西安市",
  "keywords": ["西交创新港"],
  "engines": [
    { "name": "xiaohongshu", "enabled": true, "limit": 5 },
    { "name": "deepseek", "enabled": true, "limit": 5 }
  ],
  "output_dir": ".local-data/xian/unified-runs",
  "processing": {
    "enabled": true,
    "ocr": true,
    "attraction_duplicate_meters": 10
  },
  "budgets": {
    "model_requests": 80,
    "map_requests": 60,
    "level_searches": 10
  }
}
```

目前还有可选字段engines[].keywords、publish_root和base_date。当前关键词必须是具体字符串，不会展开日期模板，也不会自行轮换或定时执行。limit表示各引擎所有关键词合计的来源上限，不是events条数。

## 2. 新设计的两份配置

| 文件 | 负责什么 | 当前状态 |
| --- | --- | --- |
| configs/collection.keyword-library.json | 关键词模板、区域组、季节主题、节日日期窗口 | 词库设计数据，尚未接入运行时 |
| configs/collection.scheduled.design.json | 引擎列表、搜索方式、轮换配额、运行时间、预算及失败处理 | 定时设计稿，schedule.enabled=false |

这两份文件不能直接传给当前npm run collect。后续由新的计划编译器读入，生成现有入口能接受的具体keywords与engines配置；实际采集继续复用现有代码，不再写另一套爬虫和分析管线。

业务规则都放JSON，运行游标、已执行任务和调用计数由脚本写入.local-data状态文件。Key和Cookie仍留在.env或本地登录目录，不写JSON。

## 3. 搜索方式与引擎分别选择

engines[].name决定渠道：xiaohongshu或deepseek。engines[].enabled决定是否使用该渠道。

拟支持engines[].search_method：

| 值 | 关键词来源 | 适用场景 |
| --- | --- | --- |
| fixed_keywords | 配置中的明确keywords | 手动测试、指定西交创新港等对象 |
| keyword_library | 从指定词组轮换、替换日期变量 | 日常定时补充 |
| seed_list | 逐个读取初始景点清单 | 后续初始化任务执行器，仍需单独实现 |

设计稿默认两个引擎都选择keyword_library。切换搜索方式、开关引擎、调整配额都改配置；没有自动凭模型生成一套无法解释的新搜索词。新增引擎仍需先注册适配器，不是填一个未知名称就能调用。

### 区域轮换

共6个区域组、14个地域词：

1. 曲江、雁塔区、长安区。
2. 碑林区、莲湖区、新城区。
3. 未央区、灞桥区。
4. 临潼区、阎良区、高陵区。
5. 鄠邑区、周至县。
6. 蓝田县。

每次区域搜索只选其中一个地域词，不把“曲江 雁塔 长安”全部拼进同一个搜索词。按组及组内游标轮换。scope=city时area为空并合并多余空格；scope=rotating_area时使用具体区域，区域词组模板必须包含area占位符。

### 日期与季节

- city采用配置keyword_city（默认“西安”）；city字段本身仍是“西安市”。
- year_month根据搜索锚点日期生成“2026年11月”等字符串，不硬编码年份。
- 夜间23:30运行默认search_anchor_day_offset=1，以次日作为未来内容的搜索锚点。base_date与星期轮换仍使用计划执行日，不把它们混成同一个日期。
- weekend_range为锚点之后最近尚未结束的周末。星期六为周六—周日，星期日只剩当日，周一到周五指即将到来的周末。同一天只渲染一次。
- next_weekend_range是上述周末之后的一组周六—周日。跨月日期保留各自月份，跨年年月正常递增。
- 季节主题配置了梅花、樱花、牡丹、踏青、荷花、夜游、红叶、银杏、室内展馆9项。日期仅决定何时尝试检索，不保证现实花期或景观仍在。
- 冬季12-01至02-28按跨年窗口解释。多个季节主题同时命中时轮换，不每天固定选第一个。
- 节日模板已经准备，但节日日历默认关闭、windows为空。春节、中秋不能凭固定公历日期或模型记忆推算；以后填入确认的当年日期窗口，或接官方日历导入后再启用。

未知变量、残留占位符、空关键词或展开后超过100字符，应在联网前报配置错误，不把模板原样发送给平台。

## 5. 默认每晚如何选词

### 小红书：1词，最多5篇

星期按计划执行日（1为周一、7为周日）：周一展览、周二市集、周三新景点、周四演出、周五周末综合、周六亲子、周日新场馆。每次在当天词组中选择下一个模板。

每4次运行可用一个有效的季节/节日词替换本次常规词，优先节日；没有有效主题时继续常规词。只替换，不额外增加小红书查询或篇数，避免7个星期固定类型被长期季节词覆盖。

### DeepSeek：5词，每词最多2篇

- 3个全市活动词：从展览、市集、演出、讲座文化、亲子5组轮换选3组，每组选下一个模板。
- 2个区域景点词：新景点、新场馆各一组，使用轮换区域，不每天重复同一个区域。
- 每2次运行可用最多1个季节/节日词替换匹配的槽位。季节词替换区域景点槽位，节日词替换活动槽位，组内替换位置也轮换；仍然合计5词。
- 两个引擎各自轮换，同一中文关键词在不同引擎可保留；本轮完全相同的“引擎＋具体关键词”在编译阶段去重，可用同组下一模板补位。

因此默认最多15篇来源：小红书5篇、DeepSeek10篇；不保证得到15条events。候选不足时报告，不在执行后偷偷换词追数量。

## 7. 定时脚本的分层

```text
系统心跳触发（建议每5分钟）
    → 读定时配置和词库
    → 检查北京时间、星期、启用状态、补跑窗口及今日执行记录
    → 获取单实例锁
    → 编译具体关键词、引擎列表、配额及现有采集配置
    → 预览，或调用现有采集流程
    → 保存每个查询的状态、实际数量、耗时及调用预算
    → 更新轮换游标并释放锁
```

拟拆为计划编译器、定时runner和系统触发器安装脚本三部分。runner不得再实现一套搜索/提取代码；应调用统一采集模块，预算贯穿整次运行，不能每个查询重新启动一次CLI而悄悄重置预算。

### 为什么系统只负责心跳

Windows任务计划程序按配置poll_minutes触发runner，实际23:30等业务时刻由runner每次读取JSON判断。以后改关键词、引擎或业务时间不必重新注册系统任务。改心跳间隔、任务名称等系统触发器参数时才重新执行安装脚本。

schedule配置包含enabled、backend、task_name、poll_minutes、at、weekdays、search_anchor_day_offset、max_runs_per_day、missed_run、catch_up_window_minutes、overlap和max_run_minutes，均写在设计JSON中。安装阶段读取这些值，不在脚本里写死23:30。

### 重复、补跑与失败

- 同一profile每日最多一次。轮询每5分钟不代表每5分钟搜索一次。
- 原计划23:30但电脑晚开机时，仅在120分钟窗口内补一次；跨午夜仍按原计划日期生成词和任务ID。超过窗口跳过，不把多日积压全部执行。
- 任务ID记录profile、计划日期和配置版本；相同任务恢复时沿用原关键词，不再抽一组新词。更改配置也不能绕过同日预算。
- 查询完成但无结果也推进该词的轮换，避免卡在空关键词上；网络失败不算完成，按原计划有限重试，成功查询不重复执行。
- 仅网络、超时、限流最多尝试2次，间隔60秒；登录失效跳过该引擎并报告，不反复打开登录窗口。已有适配器内部重试也计入总调用预算。
- 上一轮未结束时跳过，不能同时使用同一浏览器资料和写库流程。到运行时限后停止启动新查询，等待当前有界请求收尾、写检查点后再释放锁。
- 小红书重试使用独立的新输出子目录，避免再次违反MediaCrawler要求输出目录不存在的约束。
