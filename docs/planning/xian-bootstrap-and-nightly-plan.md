# 西安真实景点初始化、直接入库与定时补充方案

日期：2026-11-13。以本分支已确定的events表和采集接口作为交付契约，不再依赖其他分支README是否同步。本文只准备清单和实现方案，不执行247目标采集、不替换数据库、不创建定时任务。

## 1. 本轮交付与边界

- [景点目标清单](xian-attraction-seed-list.md)：247个目标，包括创新港校区开发者彩蛋。
- [机器清单](../../configs/xian-attraction-seeds.json)：名称、别名、地域线索、检索词、优先级及名称参考来源。
- 初始化只用DeepSeek获取内容；高德仍用于确认地点、GCJ-02坐标，不算新增内容搜索引擎。仅接收attraction。
- 后续用小红书＋DeepSeek补充景点和活动，复用统一采集入口。小红书图片走本地OCR。
- 清单不是已核验数据，不能直接当events导入。旧名录只提供名称线索，不能拿旧时间和票价填当前字段；不保证247个目标都能通过核验或去重后仍为247个点。

本地最终产物应当是应用直接读取的真实SQLite数据库。JSON、报告和原始来源仅用于诊断、重跑和追溯，不再要求他人手工把JSON导入数据库。

## 2. 数据库交付契约

继续使用现有events表：29个业务字段，暂保留start_at/end_at兼容列后共31列，不另建景点业务表。景点和活动用record_type区分，景点category为1A—5A或暂无评级，活动使用活动分类。

经纬度均为高德GCJ-02；正式保留记录必须与真实地图工具结果绑定。guide_url始终保存帖子或网页原来源，不替换成等级补查网址。时间能结构化就写valid_from/valid_to/schedule_json，不能规范的内容保留time_note和time_status。暂无评级、时间缺失不直接导致丢弃主体。

同事依托这份表结构和查询语义开发。尤其注意：unknown/conflicting时间不能当成全天开放；有些partial记录仅部分日期或时段可确认。开发者彩蛋不增加events字段，标记只存在于采集清单，展示文案以后按需要处理。

拟增加正式写入目标database_path，默认data/events.db；首次初始化与日常增量都写同一events表。database_path、任务模式和目标清单参数尚未接入当前CLI，不能把本文设想字段直接塞进现有配置运行。

### 首次替换假数据

1. 先在内部候选库完成真实采集、校验及跨来源去重，避免初始化几条数据就清掉全部演示数据。
2. 以去重后的真实可用数量、区域覆盖及字段质量验收。建议目标是至少200个不同点位；若不足就补充候选，不编造数据凑数。
3. 自动备份原数据库；使用单个SQLite写入事务，删除已明确识别为模拟数据的events记录并导入真实记录。真实已有记录按增量策略保留、合并；无法识别的旧记录不能仅凭ID前缀就删除。
4. 校验唯一性、坐标、记录类型、字段类型及integrity_check，通过后提交事务；失败回滚，不能留半张表。data目录不存在时创建新库，不假设本机已经有119条模拟记录。
5. 不清理sessions，不删表结构，不改其他业务表。旧行程若引用已移除的模拟ID，查询明确返回不存在，由主agent重新规划，不伪造对应关系。

这一步是脚本内部的自动SQL交付流程，候选库只是保证首次替换完整性的中间环节，最终直接得到应用使用的数据库。投入真实库后不再运行会清空events的模拟seed脚本。

### 日常补充

校验通过后直接按事务更新正式events；不先清库，不用每日全量重建代替增量更新。发布快照、原始资料和备份可继续保留用于回滚，但不能只更新.local-data中的CURRENT而应用仍读旧假数据文件。

## 3. 初始化搜索必须绑定清单目标

```text
目标清单／任务进度
    → DeepSeek按景点名搜索
    → 正文与目标名称、别名、地域一起交给模型
    → 模型选择高德地点，必要时补查A级
    → 目标一致性、可游览性、字段与坐标校验
    → 对照本批及已有景点去重
    → 写入真实数据库
```

每次任务带seed_id、target_name、aliases、area_hint及expected_record_type=attraction。它们属于采集任务上下文，不是新增events字段。

模型必须判断：提取的对象是否就是该目标，是否有景点、展馆、游览或校园景观的实际用途。文章顺带提到的其他机构不算当前目标完成；尤其不能把另一所学校的在建校区塞进创新港任务。未开放在建项目、单纯办公楼、学校宿舍或商业机构名不直接当作可游览景点。

创新港只放宽“必须是传统景区”这一选题限制，不放宽真实性、坐标和访问要求。保留校园主体及明确可参观的范围；对校外开放或预约条件不明确时保留说明和unknown，不宣称可以随意进入。

### 批次与检索数量

- 先10个目标验证，覆盖常见景点、普通公园、博物馆、内部子场馆和创新港。
- 通过后按每批5个目标推进。每个目标先1次DeepSeek搜索，从最多3个结果里优先选1篇适合的正文；仍缺关键事实时再用第二篇或别名补搜，不机械把所有结果都送模型。
- 按清单优先级推进247个目标，保存每个目标的完成状态和原因。异常中断后只重试未完成任务。
- 247个目标至少需要约247次初始检索；若每个目标处理1—2份正文，约247—494份正文。模型还有地图与等级工具轮次，不能把目标数当作模型调用次数。这是预算估计，不是成功率或耗时承诺。
- 当前关键词数组最多10个、引擎数量上限等仍有效；应由目标任务执行器自动拆批，不能把247个词直接放进一个现有配置。

### 同一来源与不同目标

一个政府名录或游览页面可能同时支持多个目标。网页抓取按URL和正文哈希缓存，但分析任务按“目标ID＋正文版本”记录；不能因为网页URL已处理，就把其余目标也标成完成。引用同一篇资料不代表两个不同景点应该合并。

## 4. 入库前去重与更新

| 层次 | 判据 | 处理 |
| --- | --- | --- |
| 来源重复 | 规范URL、平台内容ID、正文哈希 | 避免重复抓取和重复分析；保留来源与目标的关系 |
| 名称线索 | 正式名、明确别名、区县 | 缩小匹配范围，不能只凭相似名字就合并分馆 |
| 景点重复 | 同高德POI或GCJ-02距离≤10米 | 同一景点，保留一条主记录和所有来源关联 |
| 活动重复 | 同一场所、同一项目/届次及相同日期/场次 | 合并同场活动的多源报道；日期或届次不同不能合并 |
| 已有记录 | 对照正式库而非仅本次结果 | 更新已有主体，不能每晚增加同名新ID |

10米坐标规则继续作为景点主判据。父景区与子场馆坐标相同也可能按该规则合并，记录合并来源，不为保留数量绕过去重。若坐标不同，不能仅因都在同一园区就合并。

同一POI坐标被高德修正、漂移稍超过10米时，优先认为是既有主体更新，而非新增景点。POI变更但坐标与主体均确认一致时建立身份别名。

需要改进现有景点身份策略：景点首次入库后保留其稳定ID。后续更完整来源更新字段和主来源，而不是删除旧ID再用新帖子URL生成一个ID，避免主agent旧行程失去引用。现有批次去重会按完整度挑选代表记录，这条稳定身份策略还没有完成，需在正式初始化前补齐。

字段更新遵循：新证据可确认且更适用才更新；缺失字段不随意覆盖已确认内容。时间作为一组规则处理，避免把两个来源的开门、闭门钟点拼成一套虚假窗口。评级只更新目标自己的有效官方等级，不继承组合景区。取消、关闭或结束的明确新信息优先于旧的正常营业记录。

活动不能按坐标去重。相同场地的不同演出、展览和不同周末市集保留为不同项目/场次；时间不完整且无法判定同一届次时保留待确认，不做模糊标题批量删除。

## 5. 任务进度与时效

先用独立任务清单和运行记录保存seed_id、状态、尝试次数、下次重试时间、关联来源、关联event_id和拒绝原因；这些信息不塞进events业务字段。当前规模可先用本地进度文件和单实例锁，不扩成复杂任务平台。

状态区分pending、running、accepted、merged、not_found、deferred、retryable_failed。暂无评级或时间不完整但对象已有效保留，应算accepted，不应永远反复搜索；已合并目标记录实际保留的event_id。

网络错误和平台临时失败有限重试；明确不在西安、主体不符或在建不开放记录原因，进入deferred，不能无限补搜。同一时刻只允许一个写库任务；上次未结束时本次跳过或排队，避免定时任务重叠。

抓取成功不等于营业信息已重新确认。fetched_at记录成功读取资料，updated_at记录本地业务更新；来源发布时间与修改时间仍分别保存。不因重复抓到旧文就自动宣布旧票价、旧时段继续有效。

## 6. 后期定时补充的搜索任务

以下为北京时间的建议任务分工，不是已经创建的定时任务。

| 任务 | 建议频率/时间 | 搜索方式 | 写库方式 |
| --- | --- | --- | --- |
| 新活动发现 | 每晚23:30 | 小红书＋DeepSeek；轮换地区、展览/市集/演出等词，重点未来7—14天 | 新候选校验后增量写入 |
| 已有活动复查 | 新活动批次后 | DeepSeek按原项目、场馆、举办日期查；必要时小红书补充新公告 | 更新原ID的时段、取消/延期/结束状态 |
| 新景点补充 | 每周2—3次、小批轮换 | 小红书发现新热点，DeepSeek核实主体和可游览性 | 通过景点去重后新增或更新 |
| 已有景点轮换复查 | 每晚10—20个、优先过期字段 | DeepSeek优先，重查开放时间、预约、票价、临时闭园 | 更新原景点ID；不是每次新增一条 |
| 等级复查 | 约每30天或发现变更公告时 | DeepSeek查官方等级公告 | 只更新等级及依据 |

已有活动复查优先：未来72小时内举办、即将结束、时间冲突、延期/取消待确认的项目。网页不再命中不表示活动取消；旧文仍可访问也不表示活动继续举办。

新候选明确结束时不新增；库中已有项目确认结束时，应更新status=ended并停止被推荐，保留记录用于来源和历史行程追溯。现有pipeline会拒绝past新候选，因此“刷新已有记录”必须有独立更新路径，不能把刷新结果当普通新候选后直接丢掉取消/结束信息。

时效降级必须反映到events的status、time_status、schedule_json/time_note等字段，不能只写旁路文件而主agent读到的仍是旧的可参加时段。景点旧开放时间无法确认时，主体仍保留，时间降为unknown并记明旧依据；活动明确过期则更新ended。

小红书起步仍每晚最多一个5篇批次，先观察有效新增量再调整；DeepSeek按目标任务和已有记录复查分配配额，不让所有关键词每天全量重跑。建议先以每天最多40次正文搜索、120次主分析、60次高德、10次等级搜索作为预算讨论起点，具体依据后续实测调整，不是平台配额。达到预算就保存剩余任务到下一轮，不无限调用。

## 7. 实施顺序与自动测试

1. **正式写库与去重身份**：新增database_path和初始化/增量模式，补齐稳定景点ID、库内去重、事务回滚、模拟记录识别与备份；不改变已约定的events字段。自动测试同坐标合并、不同活动保留、跨批更新ID不变、失败不清库和不改sessions。
2. **清单驱动初始化**：实现目标上下文、attraction过滤、采集进度和拆批；先10个真实目标测试，再处理整份247目标清单。测试一文多目标、主体不符、在建误收、旧名录、创新港访问未知、断点续跑和预算上限。
3. **复查及增量**：实现已有记录刷新路径，再加入小红书＋DeepSeek发现新活动；测试结束/取消状态生效、旧来源不能无依据刷新时效、来源暂时失败不误删主体。
4. **最后接本机定时执行**：前面流程手动连续验证后再配置触发器，测试单实例锁、登录失效、网络中断和重复运行。此阶段才真正创建定时任务。

每一步修改后默认自动测试，再进行下一步。本轮清单已做数量、唯一名称、唯一seed_id、字段格式、来源引用和创新港彩蛋存在性检查；没有消耗247目标的采集API预算，也没有生成假的events填满数据库。
