## 2. 搜索范围

### 2.1 地域

- 限西安市；先覆盖碑林、莲湖、新城、雁塔、未央、灞桥及曲江、高新等常用活动区域，后补长安、临潼等市内较远目的地。
- 查询词可以使用商圈和片区，最终以场馆地址与行政归属校验。提到“西安”、作者 IP 在陕西、坐标落在粗略矩形内，都不是本地活动的充分证据。
- 咸阳和行政归属不明确的西咸新区地点单独识别，本批无法确认属西安的记录不入库。城内与远郊不在行程中假设短距离互通。

### 2.2 时间

- 首批生成基准日 D 起 14 天（含 D，至 D+13）的实际可参加时段。若按 2026-11-12 构建，则覆盖 11-12 至 11-25；真正执行时显式指定基准日。
- 搜索资料先查最近 30 天发布内容；某类不足时补查 90 天内资料。长期展览、常设项目需额外按名称查当前公告，不因最初文章较老直接排除。
- “资料发布时间筛选”与“活动参加日期筛选”分开：未来活动常由过去文章预告；刚发布的回顾文章也可能描述已经结束的活动。

## 3. 搜索数据量与停止条件

采用两批推进，先验证来源与质量，再放大。

| 批次 | 搜索预算 | 处理量 | 预期产出与门槛 |
| --- | --- | --- | --- |
| 小样本 | 5 个类别查询，Qovia 与 DeepSeek 各 5 次；每次最多 20 条，Qovia 先只取第一页 | 最多 200 次命中，去重后挑约 20–40 份高相关资料补全 | 目标 5–10 个不同真实项目，贯通至少 3 类、数个场馆；至少构建 20 条有效时段用于读库验收，若不足不凑数 |
| 正式批次 | Qovia 最多 30 组查询，每组至多 2 页；DeepSeek 最多 18 组查询，每次最多 20 条 | 最多 1560 次搜索命中；优先补全约 150–250 份去重资料 | 目标 60 个不同项目、至少 20 个不同场馆；预计 200–500 行 events，按真实场次决定 |

正式搜索预算最多 78 次请求（不含重试、详情补取与定向补查）；Qovia 的查询组由“类别 × 平台/片区”分配，不能 30 组全部被一种活动占满。近似数量不是合格活动数，不把 1000 条帖子等同于 1000 个活动。

- 独立活动数与时段行数分别统计，防止一个展览展开 14 天后虚增覆盖。
- 每组第二页仅在有后页且能增加有效资料时获取，不默认全部翻满。
- 同类连续 3 次扩搜没有新增合格项目时暂停该类，记录缺口。
- 目标达到、调用预算到达或质量不足时停止，不无限搜索；质量不达标的批次不能发布，即使数量达标。
- 定向补查、详情获取和模型调用各有独立计数与硬上限；小样本后依据成功率确定正式预算，不能让补全请求无界增长。

## 4. 搜索源设计

### 4.1 DeepSeek：网页发现与原文补全

使用官方网页搜索 `POST /v1/tools/search`，取原始结果而非让聊天模型凭记忆列活动。启用正文返回；正文缺失时单独获取对应页面，仍不可得就记录限制。

覆盖场馆与主办方官网、文旅公告、本地宝、票务项目、旅游及地方媒体。按类别查“西安 + 目标月份/展期 + 活动类型”，对已发现活动追加名称与主办方定向查证。不要用所有关键词一次 AND 查询，以免过度收窄。

DeepSeek 的 localize 参数是 IP 本地化，不是城市名称筛选；不把关键词“西安”当作已确认地域。搜索分数用于挑选补全候选，不直接作为事实可信度。

### 4.2 Qovia：社交内容发现

先使用统一跨平台搜索，重点配额分给小红书、微信公众号、微博和抖音，其余新闻、论坛、长视频等作为补充。

- 不将 `long_video` 直接映射为 B站，`short_video` 也不直接认定为快手；保留原始类别，并在实际链接能确认时细分站点。
- 跨平台第一页可能被单个平台占满，因此按平台补搜覆盖缺口。
- 首先搜索原创与转发，评论不作为活动主要依据。作者和 IP 地域不作为活动场馆位置。
- API 的 `since/until` 是资料发布时间，不传未来活动日期作为 until。
- 搜索返回 text 可能是摘要，不能默认已经取得完整活动说明。确需详情时调用对应详情接口或查主办方原文，不能拿缺失内容让模型补齐。
- 统一搜索接口目前标为 Beta，字段与实际可用性必须由小样本验证。供应商标为实时不等于我们已实测稳定，也不表示单平台全量召回。

### 4.3 事实来源优先级

按具体字段决定：场馆/主办方公告优先支持开放与变更；明确售票详情支持场次与票价；主办方社交账号可直接作为来源，普通用户体验帖用于发现并触发补查。两个转载页面不算两份独立确认。

价格、日期和预约规则有冲突时先检查对象、分馆、时间与更新公告；无法自动解决则不入库。无需依赖人工核验。

## 5. 信息处理流程

```text
确定批次参数与预算
  → 两类来源搜索、保存原始响应和计时
  → URL / 平台内容 ID 去重
  → 内容与活动候选筛选
  → 获取正文、主办方补查
  → 模型提取活动事实与原文依据
  → 本地语义与格式校验
  → 场馆匹配、坐标核实
  → 跨来源活动去重与冲突处理
  → 程序展开具体参加时段
  → 输出 events.json + provenance + manifest
  → 临时库写入、读库验收
  → 发布 events.db
```

### 5.1 模型提取

使用可配置的提取模型 API；网页搜索使用 DeepSeek 不等于提取模型已自动确定。用户已指定使用 `deepseek-flash`，配置为 `EXPLORER_COLLECTION_MODEL=deepseek-flash`，与网页搜索共用 `DEEPSEEK_API_KEY`；后续通过真实样本验证账号可用性与提取正确率。

中间结构包含：活动身份、名称、介绍、类别、分馆/场馆、地址、展期、每日开放规则、固定场次、停止入场、闭馆日、票价、预约信息、素材链接及字段依据。未知为 null，多个活动分别输出，开幕式与日常开放不混淆。

模型只提取与概括，不生成不存在的事实或最终数据库 ID。保存原文哈希、提取模型与提示词版本；空输出、坏 JSON、截断与字段错误最多有限纠正，不反复调用直到“填满”。JSON 合法不等于事实正确。

### 5.2 场馆与坐标

按标准名称、地址和分馆匹配地点；优先复用项目已有且确认为同一地点的坐标。新地点通过选定的地理编码/POI 数据源匹配地址并检查行政归属，不让模型猜坐标。

输入坐标系、来源与转换记录写进 provenance，最终统一 WGS-84。场馆有多个候选且无法消歧时不入库。地理编码供应商/凭据属于小样本接入前需要落实的依赖；不能只凭城市包围框宣称地点正确。

### 5.3 时段与费用

- 数据行对应一个可参加窗口或一场演出；连续展期逐日展开，排除闭馆日、未开放日期和已知例外。
- 常设项目也只展开本批 14 天，并需有适用的开放规则。
- 演出起止取真实场次；结束时间未知不能用估计时长冒充官方散场。现有主 Agent 对固定场次仅有窗口校验，数据本身不能完全补足此限制，交付报告需说明。
- 建议停留时长允许采用明确标记的规划估计，写入 provenance，不当成官方开放事实。
- 金额为每人费用、单位分；免费为 0，未知为 NULL。每组讲解费、押金、最低消费不能直接当每人门票；不能可靠归一时价格留空并说明。
- 图片只保存可使用的来源链接；没有图片不阻止核心活动入库，不把媒体 CDN 链接当活动信息源。

### 5.4 入库门槛

名称、类型、分馆/场馆、详细地址、经纬度、真实可参加时间窗、正停留时长及具体来源页齐全，且没有未解决关键冲突。未知费用允许、未知关键时间/地点不允许。禁止把夜间、售票期或文章发布时间误作参加时间。

不合格项目留在本地 rejected.jsonl 并带原因，可自动定向补查；补查仍失败不写 events。数据量不足直接报告，不编造。

## 6. 写入、来源字段和交付校验

### 6.1 不覆盖现有库构建

从合格 JSON 在 staging 目录创建一个全新的临时 SQLite 库，只建立 events，不创建搜索缓存/资料/活动本体表。所有中间证据用 JSON 文件管理，本次没有必要引入此前规划的整套数据库。

事务写入，稳定 ID 按来源活动身份、场馆与实际场次计算，不能按当前数组序号生成。跨平台同活动合并后保留主来源和其他证据。构建中途失败不发布半成品。

### 6.2 source_url 衔接

上游当前仍读 guide_url。此前已决定把语义改成来源网址，但改名尚未实现，不能交付一个缺 guide_url 列却宣称现有代码可直接读取的库。

推荐过渡交付：保留现有 18 列，追加 source_url（共 19 列）；新活动 guide_url 留 NULL，source_url 保存主要事实来源。这样旧后端仍能读取活动，但尚不会把新来源字段返回前端。同步列出给项目负责人的最小对接修改：Event.sourceUrl、SQLite 映射、Web source_url 及 schema 迁移；该改动必须在宣称“来源全链路可用”前完成并测试。

不将来源地址静默塞进 guide_url 伪装改名。我们只准备数据时，提供明确数据库版本与迁移说明；是否由本地补最小对接代码，实施前按分工确认，不重新扩展成搜索系统。

### 6.3 数据库发布前检查

- JSON schema、真实日期、时序、金额、经纬度、类别词表、ID/场次去重、来源与证据可定位。
- 各活动、场馆、类别、地区、日期统计；区分项目数、时段数、资料数。
- SQLite `integrity_check` 通过，表列与契约一致，JSON 图片数组可读取，JSON 与库数据数量及字段一致。
- 使用最新上游 `createSqliteEventRepository` 回查全部 ID，分日与分类查询；附近查询按真实距离排序；100 条结果上限不能被误认为库里只有 100 条。
- 对所有入库地点校验归属；对几个已知西安参考点做半径查询，不要求某一个参考点覆盖全市，也不将跨城或远郊记录硬改坐标以满足测试。
- 主数据稳定 ID，重复生成不增殖；故障回滚、空数据拒绝发布。
- 关闭所有数据库连接再交付；若使用 WAL，先完成 checkpoint/SQLite backup，交付不能遗漏未合入主文件的数据。最终发布单文件数据库并计算 SHA-256。
- 检查交付库和 JSON 不含“模拟”、虚构示例 ID/地点、密钥或用户会话数据。

## 7. 搜索延迟：如何估算及实测

用户已配置本地凭据并完成每来源 5 次真实搜索：Qovia 中位 5.863 秒、样本最大 9.190 秒；DeepSeek 中位 0.489 秒、样本最大 0.562 秒。原始记录及样本限制见首批实测报告。访问官网耗时不等于搜索 API 延迟，不使用先前假渠道测试耗时推断生产接口。

Qovia 文档只描述一般为数秒，并未据此获得我们账户的 SLA；DeepSeek 搜索文档未给出可直接依赖的延迟保证。下面均为初始工程预算，不是实测结论：

| 环节 | 单次初始等待预算 | 初始并发 |
| --- | --- | --- |
| DeepSeek 搜索（含可选正文） | 15 秒超时 | 2 |
| Qovia 搜索 | 20 秒超时 | 2 |
| 单页详情补取 | 15 秒超时 | 同域 1、全局 3 |
| 模型事实提取 | 60 秒超时 | 2 |
| 地点解析 | 10 秒超时 | 按选定供应商规则；结果缓存复用 |
| 本地校验与 SQLite 构建 | 记录实际耗时，不设网络等待 | 单写者 |

搜索瞬时失败最多重试 1 次，退避与 Retry-After 均计入耗时；鉴权、余额不足不重试，终止对应来源并报告。无明确幂等保证时，超时重试可能重复计费，必须统计尝试次数并限制总调用量。

### 7.1 小样本测速

先跑相同的 5 个查询，两个来源各 5 次；初步观察耗时和内容质量，再各补 15 次形成每来源 20 次样本。报告首请求与后续请求、成功/空结果/错误、响应体大小及 attempts。小样本 P95 仅是观测，不代表可靠长期分位数。

- 搜索延迟：从客户端发出请求到完整读取响应体，包括正文传输；重试前后耗时分别记录。
- 处理延迟：正文补取、模型提取、地点解析分别计时。
- 批次耗时：从启动到数据库发布，与单次搜索延迟分开。
- 统计 P50/P95/max、失败率、限流、总调用量、计费元数据；不只统计成功的最快请求。

### 7.2 批次量级估算

仅举计算例子：若 78 次搜索平均 5 秒，实际稳定并发 4，则理想搜索耗时约 `78 × 5 / 4 ≈ 98 秒`，另加排队、慢请求、分页依赖与重试；这不是对供应商的实测。

若 150 份资料每份模型提取 10 秒、并发 2，仅提取就约 12.5 分钟。因而本地批次很可能主要耗时在详情和提取，不能把“搜索几秒”说成整库几秒完成。最终批次预算在小样本后测量确定，当前不承诺固定分钟数。

本次为离线构建，不套用实时聊天的 12 秒单次搜索/60 秒前端预算；不更改既有聊天配置。
