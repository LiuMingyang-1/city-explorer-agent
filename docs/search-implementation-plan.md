# 西安市跨平台搜索模块总任务规划

状态：阶段 0、阶段 1 已完成并通过验证；阶段 2–6 尚未实施。本文不代表已接通任何外部搜索服务。

阶段 0 产物与验收入口：[搜索契约与存储设计基线](search-stage-0/README.md)。

阶段 1 已实现：[离线搜索骨架与最小持久化设计](search-stage-1-design.md)、[验收记录](search-stage-1-acceptance.md)。37 项搜索专项及全部 299 项项目测试通过，类型检查通过。

## 1. 数据库实际需要的表

以下为目标结构，分阶段建立，不一次性实施。保留现有活动库与会话库的职责边界，不改造 `sessions.db`。搜索资料表与活动表建议放在同一活动 SQLite 库，便于事务写回；阶段 0 已确定结构化表与现有活动表同库，快照存活动库同级目录，详见阶段 0 基线。

| 表 | 记录单位 | 用途 | 建立阶段 |
| --- | --- | --- | --- |
| `events`（现有） | 一个具体可参加时段 | 主 Agent 可引用的活动记录，供校验和前端按 ID 回查 | 保留；阶段 5 扩展 |
| `search_runs` | 一次搜索 tool 调用 | 参数、执行状态、渠道情况、耗时及失败原因 | 阶段 1 |
| `search_documents` | 一篇来源内容 | 搜索摘要、正文、原始网址、版本及获取状态 | 阶段 1–2 |
| `search_run_results` | 一次搜索中某渠道的一次命中 | 关联搜索与文档，保留查询、排名、摘要及来源渠道 | 阶段 1 |
| `venues` | 一个场馆、景点或活动地点 | 标准名称、别名、地址、坐标及开放规则 | 阶段 5 |
| `activities` | 一个活动或常态游览项目 | 活动本体、展期、状态、费用和预约信息 | 阶段 5 |
| `activity_evidence` | 一项字段的来源依据 | 关联活动与文档版本，保留提取值、原文依据及冲突处理结果 | 阶段 5 |

### 1.1 `search_runs`

- 字段：`id`、`request_json`、`mode`、`status`、`channel_results_json`、`started_at`、`finished_at`、`expires_at`。
- `status` 区分运行中、成功、部分成功、失败、取消；成功且零命中不等于失败。
- 渠道执行 JSON 保存渠道名、目标平台、实际生效的筛选条件、命中数、耗时、重试次数及脱敏错误代码。初期不单独建渠道运行表。
- 主键 `id`；按开始时间和过期时间建立查询、清理索引。
- 不存密钥，不复制完整聊天历史。与主 Agent 的 request ID 可关联，但不依赖聊天会话生命周期。

### 1.2 `search_documents`

- 字段：`id`、`platform`、`platform_content_id`、`canonical_url`、`title`、`author`、`snippet`、`content_text`、`raw_content_path`、`published_at`、`source_updated_at`、`first_seen_at`、`last_fetched_at`、`content_hash`、`fetch_status`。
- 一篇帖子、文章或票务详情是一份资料，不直接等于一个活动。一文可含多个活动，一个活动可对应多个文档。
- 优先按平台内容 ID 去重，缺失时按规范化网址去重；网址规范化只删除已确认的跟踪参数，不能删除影响内容身份的参数。
- 正文允许为空，明确区分仅搜索摘要、全文成功、不可访问、已删除、解析失败。
- `published_at` 是来源发布时间，不是活动时间；不明确的时间保留为空。
- 原始快照可放文件系统，数据库存路径和哈希。被活动证据引用的版本不可直接覆盖或随缓存清理；初期可用内容寻址文件保留版本，后续需要时再拆文档版本表。
- 网址、平台内容 ID 建唯一约束前处理空值与平台规则；按平台、获取时间建立索引。

### 1.3 `search_run_results`

- 字段：`id`、`run_id`、`document_id`、`channel`、`matched_query`、`channel_rank`、`snippet`、`final_rank`。
- `run_id`、`document_id` 分别关联搜索调用与资料；一篇资料允许被多个渠道、多个查询命中。
- 查询相关摘要放在这里，避免文档最新摘要覆盖一次搜索的实际返回信息。
- 对运行、文档、渠道和查询身份建立适当唯一约束，避免重试重复写入；按 `run_id` 和最终排名建立索引。
- 搜索返回列表去重，渠道命中记录可以保留多个。需保留本次使用的文档哈希，回放时不能误用更新后的正文。

### 1.4 `venues`

- 字段：`id`、`name`、`aliases_json`、`city`、`district`、`address`、`latitude`、`longitude`、`coordinate_source`、`opening_rules_json`、`status`、`updated_at`。
- 不同分馆分别建记录；名称相同不能作为自动合并的充分条件。
- 坐标统一为当前前端使用的 WGS-84，保留输入坐标系及转换依据；不由模型凭记忆生成坐标。
- 开放规则保留依据、适用日期、例外日期、停止入场时间。地点存在不代表某天已确认开放。
- 名称、区域可用于匹配索引；不能简单以名称设置全局唯一约束。
- 地点证据初期可随规则和坐标元数据保存；需要通用字段级溯源时再独立建关联表，不将地点事实错误归属到某个活动。

### 1.5 `activities`

- 字段：`id`、`title`、`description`、`category`、`kind`、`venue_id`、`schedule_type`、`date_start`、`date_end`、`schedule_json`、费用与预约字段、图片字段、`source_url`、`status`、`publication_state`、`last_checked_at`。
- `kind` 区分限时活动与常态游览；攻略和体验分享属于文档，不强制变成活动。
- `schedule_type` 区分自由参观窗口、固定场次、未知；展期与实际每日时段分别处理。
- 活动本体允许信息不完整；只有关键事实满足规则，才生成可规划 `events`。
- `status` 区分正常、延期、取消、结束等；`publication_state` 区分资料不完整、可规划、暂停规划。
- 同平台来源身份优先用于增量匹配；跨平台按标题、场馆、展期识别候选重复，不能仅凭相似标题自动合并。

### 1.6 `activity_evidence`

- 字段：`id`、`activity_id`、`document_id`、`document_hash`、`field_name`、`extracted_value_json`、`evidence_text`、`extractor_version`、`extracted_at`、`resolution_status`。
- 记录日期、场馆、费用、预约等字段的原文依据；模型、提示词和规则版本可追溯。
- 区分已采用、存在冲突、被更新公告替代等状态；证据引用必须对应实际提取的文档版本。
- 原文引用存在不代表理解一定正确，仍需字段语义、时间与场馆校验。
- 按活动和字段建立索引；保留旧依据，不因最终值更新而删除历史。

### 1.7 `events` 扩展与 `guide_url → source_url`

- 保留现有时段字段与 `id`，可追加 `activity_id`、`venue_id`、`schedule_type`、`status`、`last_verified_at`、`fresh_until`。
- 一个月的展览对应一个活动本体，按确认的每日开放规则展开时段；同一天两场演出生成两条时段。
- 常态景点不能生成永久有效的虚假时间窗。停止入场时间与最晚离开时间分别处理。
- 固定场次需要同步完善行程校验，现有“到访落在窗口内”不足以保证完整参加一场演出。
- 取消、失效、过期记录停止参与新搜索，但保留按 ID 回查，避免历史行程断链。阶段 0 决定保持现有“已存行程 + 当前活动详情”语义，历史快照另立升级任务。
- 将数据库 `guide_url`、TS `guideUrl` 和 Web `guide_url` 调整为 `source_url`、`sourceUrl`、`source_url`，含义改为活动主要信息来源的具体原始页面网址。
- `source_url` 不使用网站首页或搜索结果页替代；外部新增的可规划活动要求有来源，兼容旧记录时数据库可暂允许 NULL。多来源通过证据表关联。
- 迁移不得清表或重新 seed。旧攻略地址不能无条件认定为活动来源：迁移先保留旧值，只有已有明确来源语义的记录才回填新列，其余留空；旧列何时移除另设迁移步骤。
- 修改涉及 schema、`Event` 类型、SQLite 映射、seed、工具描述与输出、系统提示、Web `EventView` 映射、前端引用、文档及测试，实施前全面检索引用。
- 同步新增专用写入仓库接口；不要让搜索适配器绕过仓库直接写 SQL。活动与时段发布在事务内完成，提交后才返回可规划 ID。

## 2. 任务目标与职责

主 Agent 只调用一个搜索 tool，由主 Agent 提供搜索参数。我们负责西安市范围内的本地与跨平台外部搜索，将本次搜索取得的结果以 JSON 返回；主 Agent 使用结果选择活动、安排时间并生成行程。

本模块负责：渠道接入、搜索调度、资料获取、标准化、去重、分页、排序、缓存、必要的信息处理与合格活动写回。不负责替主 Agent 理解用户需求或生成行程。信息处理阶段可以使用模型 API 提取事实，但不增加自主规划子 Agent。

“所有搜索结果”指本次明确执行范围内获取、合并并去重的结果，不代表互联网全量。结果数量、渠道覆盖、分页、截断与失败必须明确返回；禁止无提示裁剪，也不能无限抓取或无限扩大模型上下文。

准确率优先，不设置人工核验依赖。缺失信息自动补查；仍不能确认时返回资料及限制，不发布为可规划活动。结构化 JSON 只能保证格式，不保证事实正确。

## 3. 当前代码事实与接口约束

核对依据：`src/agent/tools.ts`、`src/agent/explorer-agent.ts`、`src/agent/prompt.ts`、`src/data/types.ts`、`src/data/repository.ts`、`src/data/sqlite.ts`、`src/agent/session.ts`、`src/itinerary/validation.ts`、`src/web/types.ts`、`src/web/service.ts`。

- 当前唯一工具 `search_events(date?, category?, keyword?)` 调用 `EventRepository.search()`，只查活动 SQLite。
- 查询返回 `Event[]`，经 `JSON.stringify(events)` 进入模型工具消息，并含结构化 details；并非网页搜索结果结构。
- 本地日期按时间窗与某日重叠筛选，类型精确匹配，关键词匹配标题与介绍，最多 100 条。
- `EventRepository` 只有 `search/getByIds/close`，目前无活动增量写入接口。
- 主 Agent 提示要求只能引用工具返回的活动 ID。Planner 通过 `getByIds()` 获取详情后校验；Web service 再通过同一接口恢复行程展示与历史。
- 因此，普通搜索命中不能直接替代 `Event[]`。返回格式升级必须同时调整提示、接线和契约测试；可规划结果须具有已提交且可回查的活动 ID。
- 现有系统没有交通路线计算，搜索模块也不能承诺精确通勤时间或实时余票。

## 4. 目标 tool 契约

保留单工具入口；建议延用 `search_events` 名称，扩展内部能力。最终参数需与主 Agent 负责人确认，不默认改变其调用约定。

### 4.1 请求

兼容当前 `date/category/keyword`，评估追加查询文本、日期范围、平台范围、搜索模式、结果上限、游标及新鲜度要求。城市由服务端固定为西安市；外部传入异地条件应明确拒绝或返回范围说明，不静默跨城。使用 `Asia/Shanghai` 解释活动日期，执行时间戳采用带时区格式。

### 4.2 响应

返回版本化 JSON 对象，包含：

- `schema_version`、`search_id`、实际生效的请求参数。
- `results`：本次结果，区分 `document` 与 `event`；资料 ID 与活动 ID 分开。
- 文档字段：平台、标题、原始链接、摘要、可获取的正文片段、作者、发布时间、获取时间、实际渠道。缺失值明确表示，不伪造。
- 活动字段：`event_id`、可规划状态、时间、地点、坐标、费用、`source_url` 等，与现有 `Event` 的映射规则明确。
- `coverage`：各平台和渠道的状态、获取方式、计数、实际生效的筛选条件与限制。
- `partial`、`errors`、`truncated`、`next_cursor`：部分失败、截断及继续获取方式。

资料不完整、城市未确认、日期未确认等必须显式标记，不凭搜索关键词认定符合条件。主 Agent 可以阅读所有返回资料，但只有可规划活动可以用于 `itinerary.stops`。若只有资料、没有可规划活动，应说明限制，不编造时间或 ID。

游标需绑定请求与结果快照，后续分页不因实时结果变化出现明显重复或漏项。tool 的文本 content 与结构化响应保持一致，不只在模型读不到的 details 里保存重要状态。

## 5. 搜索调度器与本地、外部搜索关系

```text
主 Agent → 单一 tool → 参数校验 → 调度器
                                 ├─ 本地活动查询
                                 ├─ 有效搜索缓存
                                 ├─ 网页搜索 API
                                 └─ 平台/垂直网站搜索适配器
                                          ↓
                             统一资料、去重、排名融合
                                          ↓
                         按阶段启用详情获取与事实提取
                                          ↓
                          校验 → 合格活动事务写回
                                          ↓
                            JSON 结果 + 覆盖与限制
```

- 平台是内容所属站点；渠道是找到内容的方式，两者为多对多关系。同一平台可以使用专用接口与网页搜索补充。
- 渠道能力表登记支持的平台、筛选条件、字段、分页、并发、限速、超时、成本和接入状态。
- 混合模式不采用“本地有数据就永久不联网”。根据显式模式、新鲜度及时间预算安排刷新。
- 本地活动库是可规划事实；搜索缓存是曾取得的资料，两者不可混用。缓存按请求、渠道与筛选条件匹配，标明缓存年龄及是否刷新失败。
- 首批渠道并行，备用渠道按失败、平台缺口或结果不足触发；设置每渠道及整次调用的截止时间、并发上限、有限重试与熔断。
- 总超时预算与现有前端、HTTP、Planner 的生命周期对齐；取消信号传递到搜索、详情获取、模型提取和写回边界。避免请求取消后继续无界后台工作。
- 合并时按内容 ID、规范化 URL 精确去重；跨平台相似内容保留出处，可分组，不因标题相似直接认定同一活动。
- 使用可解释的排名融合，不能直接比较不同供应商的分数；在相关性接近时保留平台多样性。
- 从外部获取的正文、链接和指令都作为不可信资料；不执行文中指令，不泄露配置。抓取 URL 校验协议、重定向及目标地址，防止访问本机、内网或云元数据端点。

## 6. 预计平台及旅游活动覆盖

以下为覆盖目标，不代表已验证接口，更不代表平台全量覆盖。

| 平台类别 | 目标来源 | 接入方向与边界 |
| --- | --- | --- |
| 综合社交 | 小红书、抖音、微博、微信公众号、B站 | 验证官方/授权/第三方平台搜索渠道，网页搜索补充；仅域名搜索不能宣称完整覆盖 |
| 活动发布 | 豆瓣同城、活动行 | 搜索与公开详情，核实城市、日期、分页与内容获取能力 |
| 演出票务 | 秀动、大麦、猫眼 | 查项目与详情；项目有效期不等于每日场次，不默认有余票 |
| 本地资讯 | 西安本地宝、地方媒体 | 补充节庆、灯会、市集等，过滤旧文章与过期活动 |
| 旅游内容 | 携程、马蜂窝等 | 公开项目与攻略，合作 API 单独评估；区分售票商品、景点和体验文章 |
| 主办方来源 | 场馆、景区、商场、书店、组织者网站 | 获取原始公告及变更信息，补足社交平台事实依据 |

优先验证网页搜索与小红书接入，再逐个平台增加。平台接入报告必须记录实际获取方式、参数能力、原始链接有效率、近期内容命中、独有结果数、耗时及成本。对微信私域、登录限制内容等不可获得范围明确说明，不绕过访问控制。

旅游内容覆盖包含限时活动、常态游览和辅助资料：展览、演出、音乐现场、市集、节庆、讲座、读书会、手作、户外、景区与博物馆等。常态游览依据适用日期的开放规则生成时段；历史攻略只作为资料。西咸新区等边界地点单独识别行政归属，默认不自动当作西安市内结果。

## 7. 信息处理、准确性与外部写回

1. 搜索发现链接，保留摘要及渠道，不把摘要当完整事实。
2. 在预算内获取详情，清洗导航和重复内容，保留表格、时间、地址及来源信息。图片核心事实需要 OCR/视觉提取支持；未接入时显式说明缺失。
3. 固定结构可规则提取；长正文采用模型 API 辅助理解，输出符合 schema 的中间数据与原文证据。无需经过行程规划 Agent。
4. 本地检查类型、真实日期、时序、城市、场馆、费用单位、证据定位和冲突。模型自报置信度、多模型一致均不能替代事实校验。
5. 展期、开幕式、售票期、每日开放、闭馆日、特殊公告、固定场次分别提取，由程序生成具体时段。不以建议停留时长推导演出散场时间。
6. 缺失关键字段自动补查；失败则保留资料结果，不能填虚假坐标、免费票价或可参加时间。
7. 活动及场次身份稳定、增量更新；避免重复采集膨胀。事务提交后才能发布可规划 ID，写回失败不得返回虚假的可规划状态。
8. 来源删除或访问失败不等于活动取消；超过新鲜度阈值时限制规划资格。活动取消与延期需要明确依据。
9. 具体日期的官方变更公告可覆盖正常开放规则，但必须确认对象、分馆和适用日期；冲突无法解决时暂停发布相关时段。
10. API 价格、配额和平台能力通过接入实测确认。提取按内容哈希与提取版本缓存，避免同文重复调用。

## 8. 分阶段实施与验收关卡

规则：每阶段先落实契约与测试样本，再实现；阶段测试通过后才开始下一阶段。发现契约变化先更新本文及相关测试，不在后续阶段默认掩盖前一阶段问题。

### 阶段 0：冻结边界、接口与迁移方案

- 产物：请求/响应 JSON schema 与示例、适配器接口、渠道能力矩阵、数据表 DDL 草案、存储与清理策略、`source_url` 迁移方案。
- 明确与主 Agent 负责人的接缝：旧参数兼容、资料与活动分类、工具输出、历史回查、时间预算、取消、分页。
- 验收：正常、空结果、部分失败、仅资料、可规划活动、分页和写回失败样例均有明确语义；既有链路影响点齐全。

### 阶段 1：离线搜索骨架与最小持久化

- 实现独立搜索模块，注入假渠道；新增前三张搜索表及非破坏迁移，不替换生产 tool。
- 测试：并发上限、总超时、取消、有限重试、渠道降级、精确去重、JSON 校验、幂等保存、分页、失败与零命中区分。
- 验收：离线测试可重复通过，现有行为不变。

### 阶段 2：首个真实外部搜索渠道

- 评估并选定网页搜索服务，凭据仅在服务端配置；接入真实请求、结果标准化、缓存与原始链接。
- 测试：固定响应回放覆盖错误格式、限流、网络失败；另做受控在线冒烟验证当前可用性。
- 验收：西安测试查询可返回可访问原始链接，明确城市与日期筛选的实际能力、耗时和成本。不能只凭一次成功宣布稳定。

### 阶段 3：社交与垂直渠道逐个接入

- 优先验证小红书；随后按可用性接入抖音、微博、微信、B站、活动及票务渠道。
- 每个平台单独完成可用性报告、适配器、固定样本测试与在线冒烟，再开始下个平台；不可接通时记录限制，不伪装成功。
- 验收：渠道能独立启停，单渠道失败不阻断全局，证明相比已有渠道的新增覆盖；无效和重定向链接可识别。

### 阶段 4：本地混合搜索与结果质量

- 合并现有本地活动、有效缓存和外部命中，实现模式、新鲜度、排名融合、数量预算、分页和覆盖报告。
- 测试：本地非空仍按策略刷新、跨渠道去重、过期缓存、刷新失败、过滤条件不支持、平台结果偏斜、游标一致性。
- 验收：结果来源及可规划资格不混淆；搜索超时符合约定预算。

### 阶段 5：详情处理、活动结构化与数据库写回

- 新增地点、活动、证据表，扩展 `events`；落实 `guide_url → source_url` 迁移与全链路映射。
- 接入正文获取、规则/模型提取、场馆匹配、时段生成、写入仓库与事务发布。
- 测试：历史日期与本次展期混杂、无年份、多场演出、闭馆日、停止入场、免费但需预约、票价未知、场馆歧义、坐标系、取消延期、冲突、重复采集、部分写入失败、重试、旧库迁移与历史回查。
- 验收：只有合格记录获得可规划 ID；写回可幂等、来源可追溯、错误与不完整数据不会静默发布。

### 阶段 6：接入唯一 tool 与端到端验收

- 调整 `createSearchEventsTool` 及装配依赖，保持只有一个工具；同步提示词、响应契约、Planner 与 Web 必要接缝。
- 测试：离线真实 Agent 工具调用 → 混合搜索 → 合格写回 → 生成行程 → `getByIds` → 校验 → Web 展示；覆盖仅资料、空结果、失败、取消及重启恢复。
- 验收：既有行程与会话回归通过；前端语法检查通过；受控在线验证有真实来源链接。主 Agent 不得引用不存在或未发布的活动 ID。

## 9. 测试策略与衡量指标

- 确定性测试使用固定页面/响应快照和假渠道，不依赖实时网络或收费模型；保存脱敏样本，固定日期。
- 在线测试单独显式执行，验证渠道当前访问、鉴权、字段及限流行为；不以其替代本地回归测试。
- 每阶段运行与修改相关的测试；影响共享类型与最终集成时运行 `npm run check`，影响前端时运行 `npm run check:frontend`。
- 搜索指标：渠道成功率、原始链接有效率、可用平台数、每渠道新增结果数、重复率、近期内容命中、P50/P95 耗时、调用成本。
- 处理指标：关键字段正确率、不可确认记录拦截率、错误发布率、证据可追溯率、写回幂等性。固定标注样本用于开发测试，不引入线上人工核验依赖。
- 不宣称互联网或单平台全量召回；没有完整真值集合时不报告虚构覆盖百分比。
